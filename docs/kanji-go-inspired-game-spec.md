# 数学でGO ゲーム体験仕様（漢字でGO実プレイ観察からの適用）

## 1. 目的と境界

文化祭で初めて触る人が、説明を読まなくても「問題を見る → 手書きする → 提出する → 判定を見る → 次へ進む」を短時間で繰り返せるゲーム体験を定義する。

2026-10-03にブラウザ版「漢字でGO!」を実際に操作し、初回案内、モード／難易度／問題数の選択、ステージ導入、正答、誤答後の再回答まで確認した。本仕様で参照するのは情報設計とゲーム進行の原則だけである。名称、ロゴ、キャラクター、背景、音、固有文言、画面の正確な配置は複製しない。

## 2. 観察から抽出した体験原則

1. 問題を画面中央で最大の情報として扱う。
2. 問題番号、難易度、残機をプレイ中ずっと同じ場所に置く。
3. 正答時は大きく短い演出を返し、説明文はその後に読む順序にする。
4. 誤答を行き止まりにせず、入力を直して再回答できるようにする。
5. 問題数と難易度を開始前に選べる構造へ拡張できるようにする。
6. わからない問題を待ち続けさせず、明示ボタンと `Q` キーでスキップできるようにする。
7. 初回のロードはプレイ前に済ませ、プレイ中のテンポへ持ち込まない。
8. 将来は履歴／復習画面を用意し、遊びと学習をつなぐ。

開発者インタビューでも、Qキーによるスキップは「制限時間まで待ちたくない」という利用者要望から追加され、履歴／復習が学習機能として位置づけられている。これらは数学版にも直接適用できる。

## 3. 数学でGO向けの適用方針

漢字入力と違い、数学版では提出後に画像生成とHMER推論が入る。このシステム待ち時間をプレイヤーの回答時間に含めない。また、モデルの誤認識をプレイヤーの誤答として即座に確定しない。

### 判定の流れ

```text
手書きCanvas
  → crop済みPNG生成
  → TexTeller認識
  → 生LaTeXと正規化LaTeXを保持
  → 問題IDに紐づく正答候補と照合
  → 正解／要確認を表示
  → プレイヤーが「次へ」または「書き直す」を選ぶ
```

「要確認」の段階では残機を減らさない。「次へ（ミスを確定）」を選んだ時だけ残機を1減らす。認識結果が意図と違う場合は書き直せる。

### 判定方式

現段階は `normalized_alias` とする。

- 数式モード記号、空白、`\left` / `\right`、単一文字の不要な波括弧などを正規化する。
- 問題ごとに、項順などの許容表記を登録する。
- 一般の数学的同値性は主張しない。
- 将来は同じ判定APIの内部をSymPy等へ差し替える。

## 4. 1プレイの仕様

- じっくり練習：5問、時間制限なし。
- 20秒チャレンジ：7問、1問20秒、残り1秒につき2点の速度ボーナス。
- 初期残機：3。
- 正解：100点 + 連続正解ボーナス（1連続ごとに20点、最大100点）。
- 誤答確定またはスキップ：残機を1減らし、連続正解を0へ戻す。
- 残機0または最終問題で終了。
- 終了画面：スコア、正解数／回答数、平均フィードバック時間、残機、再挑戦。
- キーボード：`Q` でスキップ、`Enter` で提出／次へ。
- 認識、判定、結果確認中はタイマーを止める。認識エラー時は残り時間から再開する。

サンプル問題は微分、展開、方程式、指数、平方根、三角関数、式の計算を含む。問題の公開APIは正答を返さず、判定APIが問題IDを使って照合する。

## 5. 画面仕様

### タイトル／コース選択

- ゲーム名、1文の遊び方、コース差、モデル準備状態を同じ画面で確認できる。
- ページ表示直後からTexTellerを先読みし、準備完了まで開始ボタンを理由付きで無効にする。
- Phaserは開始時に遅延読込し、モデル初期化とゲーム描画コードの転送を競合させない。

### プレイ画面

- 上部：ゲーム名、コース名、スコア、連続数、残機、残り時間、モデル状態。
- 舞台：ROUND、難易度・カテゴリ、問題文、問題式、進行線。
- 回答面：白い横長Canvas。カーソル位置はリングで見える。
- 操作：提出を唯一の強い朱色操作にする。undo、clear、skipは弱い操作。
- ロード中：問題とCanvasは表示したまま、提出だけを無効化し理由を示す。

### 判定画面

- 舞台上に750ms程度の「正解」または「もう一度確認」演出を出す。
- 演出後に認識結果へ自動スクロールする。
- 認識した数式と正答を左右に比較表示する。
- 画像化、推論、判定、反応まで、PNGサイズを表示する。
- 「書き直す」は失点を確定せず同じ問題へ戻す。

### 終了画面

- スコアを最も大きく表示する。
- 正解数、平均応答、残機を二次情報として表示する。
- 同じコースへの再挑戦を唯一の強い操作にし、コース選択へ戻る操作を二次扱いにする。
- 今後の要件定義で報酬、復習、ランキング等へ差し替えられる独立面として保つ。

## 6. 状態遷移

```text
preplay ──モデル準備完了・開始──> intro ──> writing
writing ──提出──> recognizing ──成功──> result
   │                  │                    ├─書き直す──> writing
   │                  └─失敗──────────────> writing
   └─skip──> writing / finished            └─次へ──> writing / finished
writing ──時間切れ──> writing / finished
finished ──再挑戦──> intro
finished ──コース選択──> preplay
```

## 7. UX性能予算

- ページ表示：TexTeller初期化を開始し、Phaserはプレイ開始時に遅延読込する。
- P50の提出→判定：1,000ms以下を目標。
- P95：2,000ms以下を許容線。
- 3,000ms超：ゲームのテンポを損なうため改善対象。
- 判定API：P95 20ms以下。
- 認識中は全編集操作を無効化し、処理内容を表示する。
- `recognizing` と `result` 中はタイマーを停止する。

現展示版では練習コースを時間制限なし、チャレンジを20秒とし、手書き時間とシステム待ち時間を分離している。15秒案は次回プレイテストで比較する。

## 8. 実装対応

- `GET /api/v1/questions`: 公開用問題データ。
- `POST /api/v1/recognitions`: PNGからLaTeXと処理時間を返す。
- `POST /api/v1/judgements`: 問題IDと認識LaTeXから判定を返す。
- `backend/app/game_questions.py`: サンプル問題と許容表記。
- `game/src/domain/GameSession.ts`: スコア、残機、連続数、終了条件。
- `game/src/main.ts`: 設定駆動のコース、モデル先読み、タイマー、提出パイプライン、再回答、スキップ、終了画面。

## 9. 次段階

1. 50〜100件の複数筆者データでWeb実入力精度を再評価する。
2. 誤認識申告を保存し、カテゴリ別に補正候補を集める。
3. SymPy等を使う数学的同値判定を、HMER評価とは別層で追加する。
4. 別途提示されるプレイ前後UXの要件定義を、分離済みのpreplay／postplay面へ適用する。
5. 問題履歴と再挑戦キューを追加する。
