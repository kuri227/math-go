# ADR 0002: 問題データはGit管理のJSONを正本とする

- 状態: 採用
- 決定日: 2026-10-07

## 背景

数学でGOは、文化祭用PCへリポジトリをcloneまたはRelease展開して、基本的に各PC上で単独稼働させる。問題作成者が問題を追加しやすくする必要がある一方、展示準備のたびにDBサーバー、接続情報、マイグレーションを設定する運用は避けたい。

問題はソースコードとは独立して管理する必要があるが、現段階では複数人が同時に問題を編集する要件や、数万件を検索する要件はない。

## 決定

問題定義の正本を `config/game_questions.json` とする。

- 問題登録画面 `/questions/editor` は、入力をBackendで検証してから同じJSONへ追記する。
- Backendは問題一覧・正答判定・解説取得のたびに現在のJSONを読み、サーバー再起動なしで追加問題を反映する。
- JSON SchemaとPythonの検証処理で、必須項目、ID重複、難易度、正答候補を検査する。
- JSONはGitで管理し、問題追加を通常の差分としてレビュー・共有・復元できるようにする。
- ゲームコード内へ正答を重複して記載しない。

## この方式の利点

- clone後にDB作成や接続設定をせず利用できる。
- 問題の追加・削除・修正をGit差分で確認できる。
- 展示PCごとに同じ問題セットを配布しやすい。
- ファイルをコピーするだけでバックアップ・復元できる。
- 問題登録画面と直接編集の両方を利用できる。

## 制約

- 複数プロセスや複数人による同時書き込みには向かない。
- 大量データの検索、タグ集計、公開中の問題更新にはDBほど向かない。
- Releaseを読み取り専用フォルダへ展開した場合は登録できないため、書き込み可能な作業フォルダで運用する。
- 各PCで別々に追加した問題は自動同期されない。共有する場合はGitでcommitして取り込む。

## DBへ移行する条件

次のいずれかが必要になった時点で再検討する。

- 複数端末から同じ問題バンクを同時編集する。
- Web上で問題を公開・承認するワークフローを設ける。
- 問題数が増え、複雑な検索や統計を常時行う。
- アカウント、ランキング、プレイ履歴を永続化する。

ランキングやプレイ履歴だけが必要な場合は、問題JSONを維持したまま、実行データ専用にSQLiteを追加する。問題定義とプレイヤーデータを同じ保存層へ無理に統合しない。
