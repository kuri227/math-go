# ADR 0003: ゲーム画面をDisplayとControllerへ分割する

- 状態: 採用
- 決定日: 2026-10-08

## 背景

最終展示では、観客も見るモニターと、プレイヤーがペンで操作する液タブを使用する。現行の1画面レイアウトは問題と入力を同時に確認できるが、問題表示の大きさとCanvasの書きやすさが同じviewportを奪い合う。

## 決定

- モニター用Displayと液タブ用Controllerを別ブラウザーウィンドウとして提供する。
- Displayは問題、HUD、タイマー、演出、結果を担当する。
- ControllerはCanvas、編集、提出、再試行、次への操作を担当する。
- 初期構成は同一PC・同一ブラウザー・同一Originとし、`BroadcastChannel` で状態JSONを同期する。
- ゲーム進行の正本はDisplay、手書きデータの正本はControllerとする。
- 現行1画面版はフォールバックとして維持する。

## 理由

- 問題をモニターで大きく見せながら、液タブの描画面積を最大化できる。
- PNGをタブ間転送せず、Controllerから既存認識APIへ直接送れる。
- 同一PCならWebSocketサーバーを追加せず、ブラウザー標準機能で同期できる。
- 既存のPhaser、HandwritingPad、FastAPIの責務分離を保てる。

## 制約

- BroadcastChannelは別PCや別ブラウザー製品をまたぐ同期には使用できない。
- ウィンドウを目的のディスプレイへ移動し全画面化する操作は、ブラウザー制約上、初期段階ではスタッフが行う。
- 接続断、更新、重複メッセージを明示的に扱う必要がある。
- 2画面でゲーム状態を二重管理してはいけない。

## 再検討条件

- 液タブが別PCまたはネットワーク端末になる。
- 複数Controllerまたは複数Displayを同時接続する。
- ブラウザーを別製品へ分ける必要がある。

これらの場合は、FastAPIにセッション管理とWebSocketを追加し、サーバーを同期の中継点とする。
