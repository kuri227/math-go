# ランキングシステムの技術・スコア設計

更新：2026-11-03。これは技術選定と設計案であり、ランキング機能はまだ実装していません。

## 結論

本番想定を**同時稼働2〜3台・当日合計100プレイ以下**とし、初期実装は **Firebase HTTPS Function＋Firestore＋各ゲームPCのローカル再送キュー** に確定します。校内Wi-Fiでは、同じSSIDでもクライアント分離によってPC同士の通信が禁止される場合がありますが、外向きのHTTPSが通ればPC同士の直接通信なしで同期できます。

Firebaseへ送るのは本番ランキングに必要な最小データだけです。問題管理、テストプレイ、問題報告、手書き画像・筆跡、学習候補はこのPC内に残し、共有しません。設定値の受け渡し、Gitへ置くダミー値、Security Rules、App Check、XSS・API監査の実装前条件は[セキュリティ監査とFirebase導入チェックリスト](security-and-firebase-checklist.md)を正とします。

学校の許可を得た専用ルーターまたは有線スイッチを用意できる場合の **代表PC FastAPI＋SQLite** は、FirebaseへのHTTPSが校内Wi-Fiで遮断された場合のフォールバックとします。100プレイ規模で二つの同期基盤を同時運用するメリットは小さいため、通常時の二重書き込みは行いません。無許可のアクセスポイント追加も行いません。

重要な制約として、端末間通信もインターネット通信も両方使えない時間帯には、複数PC共通の順位を即時更新することはできません。その場合もプレイは止めず、各PCへ記録して復旧後に同期します。

| 観点 | 採用：校内Wi-Fi＋Firebase Functions/Firestore | フォールバック：専用LAN＋FastAPI＋SQLite |
|---|---|---|
| 端末間通信の遮断 | 影響なし。各PCは外向きHTTPSだけを使う | 専用LAN内は管理可能 |
| インターネット断 | 同期だけ止まり、プレイ記録は端末へ保留 | 影響なし |
| 導入 | Firebase SDK、Auth、Functions、管理者設定 | 代表PCのIP・ファイアウォール・配線設定 |
| 管理操作 | 管理者AuthとSecurity Rulesが必要 | 代表PCのlocalhostへ制限しやすい |
| 当日100プレイへの余裕 | 十分。無料枠を大きく下回る | 十分 |
| 注意 | Functionsの本番デプロイにはBlazeプランと請求先登録が必要 | 学校の許可と端末間接続試験が必要 |

本番1週間前までに全PCで次を確認し、その結果で方式を確定します。

1. 各PCからFirebaseのテストAPIへHTTPSで送信・取得できる。
2. Wi-Fiを一度切って再接続した後、保留記録が重複せず同期される。
3. Blazeプランの予算アラートを設定し、請求先を管理できる担当者を決める。
4. 学校側へフォールバック用の専用ルーター・有線LANの使用可否を確認する。
5. Firebaseが遮断される場合は、専用LAN案または各PCローカル記録＋終了後CSV統合へ切り替える。

## 現在の成績表示だけではランキングにならない理由

現行は正解数、連続正解、正解率、回答回数、残機を表示しますが、点数はありません。本番が固定10問になったため正解数だけの比較はできますが、次の問題があります。

- 難易度ごとの数学的負荷が違うため、全難易度を同じ表で比較すると公平でない。
- 誤答後も時間内なら再回答でき、認識・確認中は時計が止まる。最終的な正解数だけでは最初から正しく解いた人と試行を重ねた人を区別できない。
- 制限時間は15〜120秒で異なる。残り秒数をそのまま加点すると低難易度と高難易度で満点が変わる。
- 途中終了者と10問完了者を、単純な正解率だけで比べると少数回答が有利になる。

したがって、ランキングは本番ゲームだけを対象にし、難易度別に分け、サーバーがプレイ明細から点数を再計算する必要があります。テスト・開発者モード、再テスト、問題検証の結果は登録しません。

## 推奨スコア

来場者へ一文で説明できるよう、初期版では次の方式を推奨します。

```text
合計得点 = 正解した問題 × 1000点 + 速さメダル + パーフェクトボーナス

金メダル：制限時間を 2/3 以上残して正解  +500点
銀メダル：制限時間を 1/3 以上残して正解  +300点
銅メダル：制限時間内に正解              +100点
10問すべて正解                            +1000点
```

- 全難易度で1問最大1500点、10問＋パーフェクトで最大16000点です。
- 残り秒数ではなく制限時間に対する割合を使うため、15秒問題と120秒問題を同じ基準で評価できます。
- 不正解回数の直接減点は行いません。書き直す時間によって速さメダルが下がるため、同じ要素を二重に罰せず、認識誤りへの不満も減らせます。
- 連続正解ボーナスと残機ボーナスは初期版では採用しません。1回の失敗が後の問題まで影響する規則を避けます。
- 結果画面では式ではなく、`正解 8,000 + 金2個 1,000 + 銀3個 900 + 銅3個 300 = 10,200点` のように内訳を表示します。

順位表は難易度ごとに分けます。同点の場合は、`正解数が多い → 金メダルが多い → 回答に使った時間割合の合計が短い → 記録日時が早い` の順で決めます。全難易度総合順位は、参加者の選択難易度が違うため初期版では作りません。

## 保存する記録

プレイヤー名だけでなく、サーバーが再計算できる明細を保存します。

- `run_id`：1プレイの一意ID
- 難易度、開始・終了日時、完了理由、端末ID、ルール版
- 10問それぞれの問題ID、正誤、残り時間、制限時間、不正解送信回数
- サーバー計算後の得点、正解数、残機
- 表示名：任意、短い文字数制限、不適切表示へ対応できる編集・非表示状態

手書き画像・筆跡・認識LaTeXはランキングへ保存しません。学習候補とは保存目的と同意が違うため、同じテーブルへ入れません。

## 通信と障害時の扱い

1. ゲーム開始にランキング通信を必須としない。端末内で一意な `run_id` を発行する。
2. プレイ終了時、最終点数ではなく10問の明細を1回のリクエストへまとめる。
3. Cloud Functionまたは会場サーバーが、ルール版、問題数、時間上限、重複runを検証し、得点を再計算して保存する。
4. 保存成功後とランキング画面を開いたときだけ、該当難易度の上位10件と自分の順位を取得する。
5. 届かない場合はIndexedDB等のローカルキューへ保留し、「このPCに保存済み・ランキング同期待ち」と表示する。指数バックオフで再送し、同じ `run_id` の重複登録を拒否する。
6. 各ゲームPCではリアルタイム監視や短周期ポーリングを行わない。常設ランキングモニターがある場合だけ、1台でリアルタイム購読するか30〜60秒間隔で更新する。

来場者のプレイ終了画面はランキング通信でブロックしません。表示名は結果を見た後に任意入力とし、「名前を付けずに終了」を用意します。登録後は上位10件と自分の順位を表示し、次の参加者へ渡す「タイトルへ」を常に残します。

### 回線負荷の概算

2〜3台・合計100プレイでは、1プレイを「明細1回送信＋上位10件1回取得」にまとめると、書き込み約100回、上位表の文書読み取り約1,000回です。ランキング専用モニター1台が6時間、60秒ごとに上位10件を取得しても約3,600回なので、合計は約4,600文書読み取りです。Firestoreの公式無料枠は1日あたり50,000読み取り・20,000書き込みのため、想定の10倍程度の読み取り余裕があります。

通信量は、プレイ明細と上位表の各レスポンスをそれぞれ20KB以下に抑える設計目標とします。この上限では、100プレイと60秒更新のランキングモニターを合わせた本文データは約12MB以内です。TLS等の通信オーバーヘッドを含む実測値は本番前リハーサルで確認し、ブラウザーの開発者機能とFirebase Usageで記録します。

規模が小さくても短周期ポーリングに利点はありません。ゲームPCは結果表示時だけ取得し、常設ランキングモニターだけ60秒間隔で更新します。新しいスコアの反映を急ぐ場合は、スコア保存成功時にモニターへ更新通知する方式を後から検討します。

## テスト・開発者用画面に追加する管理機能

ランキング実装時は、現在の問題検証・学習データ整備と同じ入口を「テスト・開発者用画面」とし、その中を次の3領域へ分けます。

1. 問題検証：絞り込み結果の一括選択、出題順編集、エンドレステスト、問題点報告、確認状況変更。
2. 学習データ：同意付き候補保存と既存のレビュー手順への入口。
3. ランキング管理：難易度・名前・日時・端末で検索、表示名編集、記録の非表示、特定記録削除、全削除、CSV書き出し。

全削除は対象件数とバックアップ作成先を示して再確認し、SQLiteファイルの自動バックアップ後に実行します。通常ゲーム端末からの管理APIは拒否し、代表PCのlocalhostまたは管理者セッションだけを許可します。編集・削除には操作日時と対象IDを監査ログへ残します。

## Firebaseを採用する場合の条件

- 書き込みはCallable/HTTP Cloud Functionだけに許可し、関数内で点数を再計算する。
- Cloud FunctionsのデプロイにはBlazeプランが必要なため、Google Cloudの予算アラートを設定し、無料枠内でも請求先登録が必要であることを運用担当者へ明示する。
- キオスクはFirebase Anonymous Auth、管理画面は別の管理者Authとcustom claimsを使う。
- Firestore Security Rulesでクライアントからの更新・削除を拒否する。
- App Check、送信回数制限、run_idの一意制約相当を用意する。
- Firebase Admin SDKの秘密鍵をGit、ブラウザー、各ゲームPCへ置かない。
- 会場回線を切った実地リハーサルを行い、未同期表示と再送を確認する。
- FirestoreのWebオフライン永続化だけに依存しない。Cloud FunctionへのHTTP送信はアプリ側のローカルキューで管理する。
- ゲームPCで上位表の常時listenerを使わない。Firestoreは取得文書とlistener更新が読み取りとして計上されるため、結果表示時の `limit(10)` 取得を基本にする。

この条件を満たさず、Web SDKからFirestoreへ点数・編集・削除を直接許可する構成は、改ざんと誤削除を防げないため採用しません。
