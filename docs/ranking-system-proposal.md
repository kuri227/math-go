# ランキングシステムの技術・スコア設計

更新：2026-11-02。これは技術選定と設計案であり、ランキング機能はまだ実装していません。

## 結論

文化祭会場では、**代表PCでFastAPI＋SQLiteのランキングサーバーを1つ動かし、各ゲームPCが会場LAN経由で送受信する構成**を第一候補とします。インターネット障害、Firebaseの認証・権限設定、クラウド側の仕様変更に展示を依存させず、既存のPython構成と管理画面を再利用できます。

Firebase Firestoreは、会場外からも順位を見せたい、複数会場をまたいで集計したい場合の第二候補です。採用する場合もブラウザーからスコア文書を直接書かせず、Cloud Functionsで検証・再計算してから保存します。

| 観点 | 会場LAN＋FastAPI＋SQLite | Firebase Firestore＋Cloud Functions |
|---|---|---|
| 会場のインターネット断 | 影響なし | 新規送信・他端末取得が止まる |
| 既存構成との相性 | FastAPI、SQLite、管理画面を再利用 | Firebase SDK、Auth、Functionsの導入が必要 |
| 複数PC同期 | 同じLAN内で可能 | インターネット経由で可能 |
| 管理操作 | 代表PCのlocalhostだけに制限しやすい | 管理者AuthとSecurity Rulesが必要 |
| 会場外公開 | 別途構築が必要 | 得意 |
| 運用上の秘密情報 | 端末登録キー程度 | 管理資格情報をクライアントへ置かない設計が必須 |

## 現在の成績表示だけではランキングにならない理由

現行は正解数、連続正解、正解率、回答回数、残機を表示しますが、点数はありません。本番が固定10問になったため正解数だけの比較はできますが、次の問題があります。

- 難易度ごとの数学的負荷が違うため、全難易度を同じ表で比較すると公平でない。
- 誤答後も時間内なら再回答でき、認識・確認中は時計が止まる。最終的な正解数だけでは最初から正しく解いた人と試行を重ねた人を区別できない。
- 制限時間は15〜120秒で異なる。残り秒数をそのまま加点すると低難易度と高難易度で満点が変わる。
- 途中終了者と10問完了者を、単純な正解率だけで比べると少数回答が有利になる。

したがって、ランキングは本番ゲームだけを対象にし、難易度別に分け、サーバーがプレイ明細から点数を再計算する必要があります。テスト・開発者モード、再テスト、問題検証の結果は登録しません。

## 推奨スコア

正解した各問題について、次の点数を加算します。

```text
問題得点 = max(0,
  1000
  + floor(500 × 回答時の残り時間 ÷ その問題の制限時間)
  - 200 × その問題の不正解送信回数
)
```

- 全難易度で1問最大1500点、10問最大15000点。制限時間の違いを割合で正規化する。
- 時間切れ・未正解は0点。残機そのものには加点せず、正解数と速度へ結果が反映されるようにする。
- 連続正解ボーナスは採用しない。序盤の1回の失敗が後続問題まで影響せず、初見客にも説明しやすい。
- 不正解を繰り返す総当たりを抑えるため、1回200点を減点する。認識誤りの場合は確認画面で書き直せるため、意図と違う認識を送信しない導線を維持する。

順位表は難易度ごとに分けます。同点の場合は、`正解数が多い → 不正解送信が少ない → 手書き中の合計時間が短い → 記録日時が早い` の順で決めます。全難易度総合順位は、参加者の選択難易度が違うため初期版では作りません。

## 保存する記録

プレイヤー名だけでなく、サーバーが再計算できる明細を保存します。

- `run_id`：1プレイの一意ID
- 難易度、開始・終了日時、完了理由、端末ID、ルール版
- 10問それぞれの問題ID、正誤、残り時間、制限時間、不正解送信回数
- サーバー計算後の得点、正解数、残機
- 表示名：任意、短い文字数制限、不適切表示へ対応できる編集・非表示状態

手書き画像・筆跡・認識LaTeXはランキングへ保存しません。学習候補とは保存目的と同意が違うため、同じテーブルへ入れません。

## 通信と障害時の扱い

1. ゲーム開始時にランキングサーバーから短時間有効なrun tokenを受け取る。
2. プレイ終了時、クライアントは最終点数ではなく問題ごとの明細を送る。
3. サーバーがルール版、問題数、時間上限、重複runを検証し、点数を再計算してSQLiteへ保存する。
4. 保存成功後とランキング画面を開いたときに、該当難易度の上位記録を取得する。
5. サーバーへ届かない場合はゲームPCのローカルキューへ保留し、「このPCに保存済み・ランキング同期待ち」と表示する。復旧後に同じrun_idで再送し、重複登録を防ぐ。

来場者のプレイ終了画面はランキング通信でブロックしません。表示名は結果を見た後に任意入力とし、「名前を付けずに終了」を用意します。登録後は上位10件と自分の順位を表示し、次の参加者へ渡す「タイトルへ」を常に残します。

## テスト・開発者用画面に追加する管理機能

ランキング実装時は、現在の問題検証・学習データ整備と同じ入口を「テスト・開発者用画面」とし、その中を次の3領域へ分けます。

1. 問題検証：全問題選択、エンドレステスト、問題点報告、確認状況変更。
2. 学習データ：同意付き候補保存と既存のレビュー手順への入口。
3. ランキング管理：難易度・名前・日時・端末で検索、表示名編集、記録の非表示、特定記録削除、全削除、CSV書き出し。

全削除は対象件数とバックアップ作成先を示して再確認し、SQLiteファイルの自動バックアップ後に実行します。通常ゲーム端末からの管理APIは拒否し、代表PCのlocalhostまたは管理者セッションだけを許可します。編集・削除には操作日時と対象IDを監査ログへ残します。

## Firebaseを採用する場合の条件

- 書き込みはCallable/HTTP Cloud Functionだけに許可し、関数内で点数を再計算する。
- キオスクはFirebase Anonymous Auth、管理画面は別の管理者Authとcustom claimsを使う。
- Firestore Security Rulesでクライアントからの更新・削除を拒否する。
- App Check、送信回数制限、run_idの一意制約相当を用意する。
- Firebase Admin SDKの秘密鍵をGit、ブラウザー、各ゲームPCへ置かない。
- 会場回線を切った実地リハーサルを行い、未同期表示と再送を確認する。

この条件を満たさず、Web SDKからFirestoreへ点数・編集・削除を直接許可する構成は、改ざんと誤削除を防げないため採用しません。
