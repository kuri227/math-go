本書は、文化祭での最終展示に向けた「数学でGO」のゲーム面・システム面の実装基準である。2026-10-06に参照できたNotionページ「数学でGO 要件定義」を要求の入力として使うが、内部設計をそのまま複製するものではない。

- 参照元: [数学でGO 要件定義（Notion）](https://app.notion.com/p/GO-3ed779287ae880ed8d35ed24cea1a6ae)

競合時は、文化祭での初見操作、認識モデル固有の制約、実測性能、保守性を優先し、採否と理由を本書へ残す。

## 2. Notion資料から取得した要求

### 2.1 ゲームの目的

- 「ファイブツアーズジェット」や「漢字でGO」のように、制限時間内に問題へ回答し、正解して次へ進む。
- 四則演算が可能な小学生以上を主な対象とする。
- Webアプリが問題表示と入力可視化を担当し、OSSのHMERモデルが手書き画像をLaTeXへ変換する。

### 2.2 機能要求

- FR-01: 問題を徐々に大きくし、残り時間に応じた緊迫感を出す。正解・時間切れ・中断後は、問題、正答、解説を表示し、プレイヤー操作で次へ進む。
- FR-02: 7段階（小学校低学年、小学校高学年、中学校、高校、高専、大学、大学院）を想定した難易度選択を提供する。カードをページ単位で入れ替えられる拡張可能な構造にする。
- FR-03: 板タブ・タブレット等から手書き入力し、画像としてHMERモデルへ渡してLaTeXへ変換する。
- FR-04: 問題の正答候補と認識LaTeXを比較する。未約分、未整理、計算途中を誤答にできる問題設計を行う。解けない場合は中断操作を提供する。

### 2.3 非機能要求

- NFR-01: 問題はローカルJSONから読み込む。基本項目は `question`、`answer`、`description`、`difficulty` とし、数式はLaTeXで記述する。
- NFR-02: 手書き変換待ちを短くする。限界がある場合は認識・判定中にゲーム時計を止める。
- NFR-03: PC操作に不慣れな来場者のため、キーボード・マウス操作を減らし、矢印と決定を中心にする。

## 3. 採用判断と競合分析

| 論点 | Notion案 | 既存実装 | 採用方針と理由 |
| --- | --- | --- | --- |
| 難易度 | 7段階 | 練習／チャレンジ／マラソンの3コース | 両方を別軸として扱う。難易度は問題内容、コースは時間と問題数のルールを決める。 |
| 問題データ | ローカルJSON | Python内の固定データ | JSONへ移す。非開発者が問題追加でき、ゲームコードと正答データを分離できる。 |
| 時間切れ | 解説後、操作で次へ | 約850ms後に自動遷移 | Notion案へ変更する。展示では読み終える前の遷移が混乱を生む。 |
| 中断 | 誤答として解説へ | スキップ後すぐ次へ | 「わからない」に改称し、正答と解説を表示してから次へ進む。 |
| 誤答 | 解説後、次へ | HMER誤認識なら書き直せる | 既存仕様を残す。認識誤りを知識の誤りとして扱わないことが数学版では重要。 |
| 判定 | 完全一致を基本に問題別汎用性で補う | 正規化LaTeXと別表記 | 既存方式を継続する。一般的数学同値性は別レイヤーとして後日導入する。 |
| 二値画像 | 画像をOSSへ入力 | crop済みPNGを送信 | 既定の二値化は採用しない。前処理A/Bで精度向上が確認できた場合だけ切り替える。 |
| 問題拡大 | 時間とともに拡大 | 問題切替時のみ短い拡大 | 残り時間に応じた上限付き拡大へ変更する。可読性を壊さない範囲に制限する。 |
| 音 | 終了直前アラート | 音なし | 短い警告音を追加し、常時見えるON/OFFを用意する。会場運用で音を切れるようにする。 |
| 高難度コンテンツ | 大学院まで | 7問の基礎サンプル | 7段階の器を実装し、展示用サンプルを用意する。正答候補は運用前レビューを必須にする。 |

## 4. 最終展示版のゲームフロー

```text
タイトル
  → 難易度選択（7段階）
  → コース選択（練習／チャレンジ／マラソン）
  → モデル準備完了
  → ステージ導入
  → 問題表示・手書き
  → 認識・判定（時計停止）
  → 正解／要確認／時間切れ／わからない
  → 正答と解説
  → 書き直す または 次へ
  → 全問終了／残機0
  → 結果
```

### 4.1 難易度

1. 小学校低学年
2. 小学校高学年
3. 中学校
4. 高校
5. 高専
6. 大学
7. 大学院

選択値は出題難易度の上限として扱う。まず選択段階の問題を入れ、必要数に満たない場合は直下の段階から復習問題を補う。これは展示初期の問題数不足を安全に扱う暫定ルールであり、JSONの問題数が増えれば選択段階だけで構成できる。

### 4.2 コース

- じっくり練習: 5問、制限時間なし、残機3。
- 20秒チャレンジ: 7問、1問20秒、残機3、残り時間ボーナスあり。15秒案は次回プレイテストで比較する。
- 30問マラソン: 30問、制限時間なし、残機5。選択難易度以下の候補が不足する場合は、その範囲内で循環する。

### 4.3 1問の状態

- `writing`: 入力可能。問題は経過時間に対して非線形に拡大する。最大1.6倍を基本とし、積分・分数・行列など背の高い式は実寸から安全な上限（最低1.35倍）を算出して、見出しや回答欄との重なりを防ぐ。
- `recognizing`: CanvasをcropしPNG化、TexTeller認識、判定。時計と入力を停止する。
- `result`: 正誤、認識数式、正答、解説を表示する。
- `retry`: 認識結果が意図と違う場合は失点せず同じ問題へ戻る。
- `advance`: 正解またはミスを確定し、次の問題へ進む。
- `reveal`: 時間切れ・「わからない」では認識を行わず、正答と解説を取得してから進む。

## 5. 問題JSON

保存先を `config/game_questions.json` とする。

```json
{
  "questions": [
    {
      "id": "solve-linear",
      "question": "2x + 6 = 0",
      "question_latex": "2x+6=0",
      "instruction": "方程式を解きなさい",
      "answer": ["x=-3", "-3=x"],
      "description": "両辺から6を引き、2で割ると x=-3。",
      "difficulty": 3,
      "category": "方程式"
    }
  ]
}
```

制約:

- `id` は全体で一意。
- `question` は読み上げ・フォールバック用、`question_latex` はKaTeXによる構造表示用とする。
- `answer[0]` を表示用の模範解答とする。
- `answer` の各値は正規化後に重複しないこと。
- `difficulty` は1〜7。
- 近似問題は丸め規則を `instruction` と `description` に明記する。
- 問題APIは正答を公開せず、判定または解説APIを通じてプレイ後に返す。

## 6. API境界

- `GET /api/v1/questions`: 問題文、カテゴリ、難易度だけを返す。
- `POST /api/v1/recognitions`: crop済みPNGをTexTellerへ渡し、LaTeXと計測値を返す。
- `POST /api/v1/judgements`: 問題IDと認識LaTeXを受け、正誤、模範解答、解説を返す。
- `GET /api/v1/solutions/{question_id}`: 時間切れ・中断時の模範解答と解説を返す。
- `POST /api/v1/admin/questions`: ローカルの問題登録画面から検証済み問題を追加する。

HMERモデルはゲーム進行から切り離し、既存のRecognizer interfaceと比較評価資産を維持する。

## 7. UX・性能要件

- ページ表示直後からTexTellerを先読みする。
- モデル準備完了まで開始操作を理由付きで無効化する。
- 提出から結果表示のP50目標は1,000ms以下、P95許容線は2,000ms以下。
- 3,000msを超えた場合は改善対象として計測値を残す。
- 認識・判定・解説確認中は回答時計を止める。
- 警告音は残り5秒以下で段階的に鳴らし、ユーザーが常に無効化できる。
- マウス、ペン、タッチ、キーボードに対応する。
- `prefers-reduced-motion` では接近演出を抑制する。
- 主要操作は各状態で1つに絞り、理由のない無効状態を作らない。

### 7.1 次期2画面構成

最終展示では、問題を見るモニターと、手書きする液タブを論理的に別画面へ分割する。物理ディスプレイへ配置するため、同一ブラウザーのDisplay用ウィンドウとController用ウィンドウを使用する。

- Displayは問題、HUD、タイマー、正誤演出、正答、解説、最終結果を表示する。
- ControllerはCanvas、1画戻す、全消去、わからない、提出、書き直し、次への操作を表示する。
- ゲーム状態の正本はDisplay、strokeと入力画像の正本はControllerとする。
- 初期構成は同一PC・同一Originとし、状態同期には `BroadcastChannel` を使用する。
- Controllerはcrop済みPNGを認識APIへ直接送り、画像本体を画面間で転送しない。
- 現行1画面版は、開発時・接続失敗時・展示トラブル時のフォールバックとして残す。

実装順、同期メッセージ、切断時の扱い、受入条件は `docs/dual-screen-game-design.md` を正とする。

## 8. 最終展示へ向けた完了条件

1. 7段階の難易度と3コースを選べる。
2. JSONの差し替えで問題を追加できる。
3. 時間切れ・中断を含む全終了経路で正答と解説を確認できる。
4. 認識誤りを失点前に書き直せる。
5. モデル待ち時間と推論時間をプレイ時間から除外する。
6. 現行1画面版がデスクトップとタブレット相当幅で破綻せず、次期2画面版ではDisplayとControllerの各想定解像度でスクロールなしに主要要素が収まる。
7. API、ゲーム、Python、TypeScriptのテストが通る。
8. 既存のモデル比較結果、独自収集データ、Release資産を変更しない。

## 9. 保留事項

- 一般的な数学的同値判定（SymPy等）。
- ランキング、復習履歴、報酬、BGM。
- 複数端末同時接続と会場LANの長時間負荷試験。
- 各難易度で十分な問題数と複数筆者の認識精度を確保すること。
- 液タブとモニターの実機解像度、OS表示倍率、ブラウザー固定可否。
- 2画面版の切断復旧、二重送信、タイマー同期を含む30分以上の実機試験。
