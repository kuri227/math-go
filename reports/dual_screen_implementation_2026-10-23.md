# 2画面Controller実装・検証記録（2026-10-23）

対象：操作の液タブ集約、初回3秒予告、回答筆跡同期、独立メモ。作業ツリー上の通信版v4。

## 実装した契約

- Controllerでモード・難易度・テスト問題を選び、ガイド、開始、読み取り、回答、次問、再テスト、終了、再プレイを操作する。
- Displayの`Session`だけが設定を検証して進行を確定する。Controllerへ`Session`を追加しない。
- Controller用Snapshotでは問題本文・数式・正答・解説を空にし、プレイ中の問題内容を液タブへ複製しない。
- 初回は`countdown`へ遷移し、ControllerがCanvasを表示して`controller-ready`を返してから3秒予告を進める。予告中は問題・入力・時計を開始しない。切断時はガイドへ戻す。
- 次問と再テストは秒数を固定せず、空の回答用紙snapshotとreadyを受領してから開始する。
- 回答Canvasはローカル描画を待たせず、縦横比付き正規化座標の全体snapshotを最大約25Hzで送る。再接続時にも全体を再送する。旧run・旧question・旧generationを拒否し、12,000点を上限にする。
- 回答とメモは別Canvas・別undo履歴。メモには通信コールバックを持たせず、認識PNG・crop・筆跡JSON・学習候補保存は回答Padだけを参照する。
- 全消去は現在の用紙へ即実行し、取り消し履歴を追加しない。終了操作は上部ツールバーへ分離する。

## Computer UseによるUI・UXテストと反映

Chrome上の実画面で、2画面接続、設定、テスト問題選択、ガイド、開始同期、3秒予告、問題公開、回答／メモ切替、空欄認識のエラー回復、途中終了、Displayの最終結果、Controllerからの再プレイを操作した。サーバー再起動後も両タブが再接続し、「2画面接続済み」へ戻ることを確認した。

実画面では、メモ用紙へ切り替えた後も下部案内が「答えを書いて『読み取りを確認』」のままで、メモも認識対象に見える不整合があった。修正後は「採点・保存・モニター同期の対象外」「回答は回答用紙」と明示されることを同じComputer Use操作で再確認した。

2026-10-23の再検証ではComputer Useのドラッグ入力が利用可能になった。回答Canvasへ実マウスドラッグを送り、Controller上の描画、Displayへの筆跡同期、TexTellerへの画像送信、認識結果確認、誤答判定、Display上の正答・解説表示まで通した。メモCanvasでは、案内文がCanvasを覆い、ドラッグが文字選択になる不具合を発見した。回答・メモのCanvas、案内、ポインターを共通クラス化し、`touch-action:none`と`pointer-events:none`を両用紙へ同じ契約で適用した。修正後は案内文上からでもメモへ描画でき、undoで消せること、Displayへは筆跡が送られないことを再確認した。

保守性レビューでは、Controllerへ渡す情報制限と状態別案内が`App.ts`内の長い条件式へ混在していた点を改善対象とした。`presentation.ts`へ純粋関数として分離し、問題・正答・解説をControllerへ出さない境界とメモ案内の優先順位を3件の単体テストで固定した。PairHubもメッセージ検証を純粋関数へ分離し、通信ループと検証規則を独立して変更・検査できる形にした。Canvas修正ではID別のCSS追加を避け、`drawing-pad`、`pad-hint`、`pad-pointer`の共通クラスへ入力契約を集約し、両用紙が同じ構造を持つことを構造テストで固定した。

Computer UseのChromeタブで連続ドラッグ、認識、採点まで確認したが、入力は実マウス相当であり物理液タブのペン、筆圧、傾き、Palm rejectionは未検証。ブラウザーのviewport overrideとズームキーはChrome拡張タブの`innerWidth`へ反映されなかったため、320px狭幅と125〜200%拡大率は未合格のままとする。

## 2026-10-28 表示回帰の修正

添付画面で確認された「残り秒数が小数になる」「結果カードが回答中の筆跡・状態文と衝突する」回帰を修正した。残り時間はミリ秒から切り上げた非負の整数秒として表示し、Displayの回答筆跡は回答中の4フェーズだけに限定した。結果フェーズでは重複する状態文も隠し、問題と結果カードの間隔を明示的に確保した。

`presentation.ts`へ秒数変換と表示条件を純粋関数として集約し、境界値とフェーズ別表示を3件追加して固定した。ライブリージョンは先に非表示状態を確定してから文言を更新し、結果遷移時の重複読み上げも避けた。

Computer Useで本番ビルドをChromeのController／Display 2タブに読み込み、19秒から0秒まで整数だけが表示されることを確認した。時間切れ後は添付画像相当の955×779pxで、問題領域の下端198px、結果カード上端222px（24px間隔）、回答筆跡と重複通知は非表示・高さ0だった。Vitestは17ファイル605件、TypeScript型検査とVite本番ビルド、`git diff --check`はいずれも成功した。

同日の再報告では、開いたままの旧ページが以前のハッシュ付き資産を保持し、`0.0秒`と旧レイアウトを表示していた。HTML 3入口へ`Cache-Control: no-store`を付け、再読込時に常に現在のハッシュ付き資産を参照するようにした。結果画面の構造も、問題表示・回答筆跡・結果の縦積みから、問題と正答・解説を1枚の結果カードにまとめた2列構成へ変更した（760px以下は1列）。

Computer Useで更新サーバーを再起動し、1176×829pxのChromeで本番モードを時間切れまで操作した。結果カードは上端175px〜下端508px、文書全体は829pxでスクロール不要だった。回答筆跡、旧問題領域、重複通知は非表示で、問題と正答は各509px幅の2列に収まった。18秒から0秒まで整数表示であること、配信HTMLが`no-store`と新しいアセットハッシュを返すことも確認した。

## 2026-10-28 UI・UX全体回帰監査

Chromeの実画面をComputer Useで操作し、設定、ガイド、1画面回答、2画面Display、認識待ち、認識確認、正解結果、時間切れ結果を確認した。画面幅は1440、955、760、320pxを対象にし、横方向のはみ出し、主要操作の視認性、フォーカス順、タップ領域、表示重複、結果遷移を検査した。自動検査はVitest 17ファイル605件、TypeScript型検査とVite本番ビルド、`git diff --check`が成功した。

監査で、Displayの回答画面が一般的な低い画面高で不要な縦スクロールを生むこと、1画面モードの結果時に旧問題領域と案内が残って縦方向へ重複すること、旧領域を隠すだけでは回答者が自分の提出内容を結果で確認できなくなることを検出した。Displayの回答領域を`svh`基準で画面高へ追従させ、結果時は問題・提出回答・正答例を同じ結果カードへ集約した。提出回答がない時間切れでは回答列を出さず、狭幅では固定列数を使わず1列へ落とす。結果時の重複案内と旧問題領域も1画面・Displayの両方で隠した。

修正後、955px級の1画面モードで実マウス相当のドラッグにより「3」を書き、TexTellerの認識確認、回答確定、正解結果まで通した。結果カードには「問題」「あなたの回答」「正答例」が3列で表示され、文書幅943pxに対しviewport幅958pxで横スクロールは発生しなかった。2画面Displayでは回答中の主要内容が高さ910px内へ収まり、時間切れ結果でも問題と正答が同じカード内に表示された。320pxでは横スクロールなしで1列化し、内容量に応じた縦スクロールだけが発生した。

保守性レビューでは、結果専用の別画面を増やさず既存の`result`領域へ3つの意味的な小領域を追加し、表示条件を既存の状態更新へ集約した。列数は状態ごとの固定指定ではなく`auto-fit`で決まり、回答あり・時間切れ・狭幅を同じ構造で扱う。重複案内の条件は`presentation.ts`の純粋関数へ置き、1画面結果とDisplay結果の両方を単体テストで固定した。

残る検証境界は、Canvas回答にキーボードだけで数式を入力する代替手段がないこと、スクリーンリーダー実機、物理ペンの筆圧・傾き・Palm rejection、長時間運用を未検証であること。したがってWCAG適合や展示実機合格は主張しない。`impeccable detect`は実行環境に監査エンジンがなく利用できなかったため、ソース確認、ブラウザー実操作、寸法・コントラスト検査、自動テストで代替した。

## 2026-10-30 本番導線・効果音・モデル起動の仕上げ

来場者用画面をタイトル、遊び方、難易度選択、開始案内、ゲーム、結果、同レベル再挑戦・難易度選択・タイトル復帰の流れへ整理した。技術説明と学習データ運用文は来場者導線から外し、問題テストと同意済み学習候補保存はタイトルの「スタッフ用」から到達できる形で維持した。結果画面も内部集計の「回答送信回数」ではなく、正解数・挑戦数・残機を表示する。

効果音は実行時生成ではなく、リポジトリの生成スクリプトで事前作成した8個のWAVを配信する。クリック、開始、正解、不正解、時間切れ、終了、通常・緊急tickを共通クラスから再生する。ヘッダーには0〜100%の音量スライダーを追加し、0%をミュートとして扱う。設定はブラウザーに保存し、同一Originの別画面にも反映する。

Computer Useでは本番FastAPIを実際に起動し、タイトル→難易度→開始案内→カウントダウン→回答→途中終了→結果→再挑戦等の導線を操作した。320×568pxで開始案内と主要ボタンが収まり、回答画面では固定操作バーがCanvasを覆う不具合を検出した。狭幅・低画面の操作バーを通常フローへ戻し、スクロール後に回答Canvas、取り消し、消去、読み取り確認が重ならず表示されることを再確認した。音量は70%表示、0%ミュート、再読込後の保持、320pxと通常幅での収まりを確認した。

通常のGPU起動は`HMER_EAGER_MODELS=texteller`でTexTellerだけを先読みする。`/models`の実測はTexTellerがCUDAで利用可能、UniMERNetは未読込だった。ASGI起動中の同期読込をバックグラウンド化し、ヘルスチェックが`loading`と失敗詳細を返せるようにした。起動スクリプトとワーカーの180秒競合には15秒の診断余裕を設け、10秒ごとの進捗を表示する。

RTX 3050 Laptop GPUでのクリーン起動は19.85秒、ワーカー計測17.43秒だった。内訳はPython/PyTorch 4.31秒、TexTeller import 5.94秒、1.19GBの重み読込6.34秒、CUDA転送0.60秒、tokenizer 0.23秒。過去ログには`CUDA_ERROR_UNKNOWN`とsticky CUDA contextがあるため、以前の3分超は通常のモデル読込速度ではなく、GPUコンテキスト異常または再起動重複の可能性が高い。今後は`results/logs/texteller.log`の`[startup]`行で停止工程を特定できる。

自動検査はVitest 17ファイル605件、TypeScript型検査・Vite本番ビルド、対象Python回帰1172件が成功した。物理液タブ、会場音量、長時間連続運転、スクリーンリーダー実機は引き続き実機確認が必要であり、今回の結果だけでそれらを合格とはしない。
